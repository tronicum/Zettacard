# Kanban / Scrumban working agreement

No fixed sprints. Cards flow continuously through columns, pulled (not pushed) by whoever is doing Developer or Student work in a given session. The board itself lives in `../BACKLOG.md` as plain markdown checklists — no external tool needed at this scale.

## Columns

`Backlog → Ready → In Progress → Student Review → Done`

- **Backlog** — ideas and known future work, unrefined. Anyone can add here.
- **Ready** — PO has written acceptance criteria; a Developer can pick this up without needing to ask clarifying questions first.
- **In Progress** — actively being worked. **WIP limit: 2.** Don't start a third card while two are in progress — finish or explicitly park one first.
- **Student Review** — implementation done, validation passed, now being read as a learner would read it. Only Student-persona review happens here, not new development.
- **Done** — passed Student Review, committed to git with the card ID in the commit message.

## Definition of Ready

A card can move Backlog → Ready only when it has:
- A clear, testable acceptance criterion (e.g. "N questions, topics X, locales Y, schema-valid, legal_basis filled")
- Confirmation it doesn't conflict with the non-negotiable constraints in `AGENTS.md` (no catalog-sourced content, license attached, etc.)

## Definition of Done

A card can move Student Review → Done only when:
- Schema validation passes (unique IDs, matching option keys across locales, correct-answer keys present, license/meta fields intact)
- Student Review found no confusing wording or exam-unrealistic content left unresolved
- Changes are committed with `[<card-id>] <summary>`

## WIP limit rationale

Two in-progress cards keeps context switches low and makes it obvious when something is stuck (if both slots are full and neither has moved in a while, that's a signal for the Scrum Master to intervene, not to open a third).

## Retro log

Add a dated, 3-bullet note here after each completed batch of cards: what worked, what didn't, one change for next time. Keep it short — this is a working log, not a ceremony.

### 2026-08-04 — Pilot batch (DN-0, retroactive)
- Worked: fact-layer/text-layer schema held up cleanly across both a text-heavy topic (Vorfahrt) and an image-anchored one (Verkehrszeichen) — good sign it generalizes to the rest of Grundstoff.
- Didn't: no Student Review pass actually happened before delivery (board didn't exist yet) — the 50 pilot questions should get one retroactively before more topics are added.
- Change: from now on, no card reaches Done without going through Student Review first, even for small batches.

### 2026-08-04 — Sprint 1 MVP (DN-13)
- Worked: the fact-layer/text-layer schema made the whole language-switch feature nearly free — the app just re-renders from `text[lang]`, no separate data pipeline needed per locale.
- Didn't: initial build put the language switcher only in the sticky header, which is a full-screen overlay away from the detail view — meaning it was literally impossible to switch languages while reading a question, the single most important interaction for this sprint's goal. Caught by an automated click-through pass (Playwright), not by eyeballing the code.
- Change: for UI cards going forward, the "click through as a real user" verification step happens before calling something Done, not after — automate it where possible instead of relying on a visual read of the code.

### 2026-08-04 — First real Student + UX persona runs (DN-1, DN-17)
- Worked: running Student and UX as genuinely independent agents (no visibility into each other's findings, real tool access — one cold-answered all 50 questions, one actually drove the live app in a browser) surfaced things a self-review never would have: the UX pass found 3 P0s (back-gesture exits the app, scroll resets every navigation, reveal-answer drops focus) that the earlier "automated click-through" pass in DN-13 didn't catch, because that pass tested function, not real usage patterns like the phone back gesture.
- Didn't: while fixing the UX findings and adding a PO-requested light/dark theme in the same pass, introduced a fresh bug — header background and topic-badge text color were hardcoded to dark-theme values, so light mode was nearly unreadable. Caught by re-running the same verification discipline (screenshot + read it) before committing, not by a separate review pass.
- Change: UX is now a standing fifth persona (see docs/PERSONAS.md), not a one-off ask — any new UI work gets a UX pass before Done, same as Student gates content. Also: any theming/styling change needs a screenshot check in BOTH themes before commit, not just the one being actively worked on.

### 2026-08-04 — Low-literacy Student check + formal accessibility audit (DN-17, DN-23)
- Worked: two more independent-agent runs (a low-German-literacy reader persona, and a formal WCAG/BITV audit) found real, concrete bugs a fluent-reader review and a general heuristic UX pass had both missed: 4 color-contrast failures (dark-theme accent, light-theme correct-mark green, hardcoded white text on the active filter pill, a badge background invisible in light mode), the detail view had no dialog semantics or focus trap at all, `<html lang>` never synced with the in-app language toggle, and sign/diagram alt text was just the raw internal code (e.g. `"274-50"`) instead of a real description. Also self-caught, while wiring proper alt text: the 7 Vorfahrt diagrams baked the priority-badge answer directly into the image, spoiling the question before the user attempted it — fixed by splitting plain/answer SVG variants.
- Didn't: none of these had been checked at all before this round — accessibility and plain-language readability were treated as "nice to have later" rather than standing gates, even though the target audience (nervous test-takers, some with limited German, on mobile) is exactly who these issues hit hardest.
- Change: both checks are now formalized as standing dimensions in docs/PERSONAS.md (low-literacy read under Student, formal a11y audit under UX) — run at least once per content/UI milestone, not as one-off asks. All findings from this round were fixed and verified (Playwright: dialog focus, inert focus-trap, lang sync, diagram swap, keyboard walkthrough; screenshot: light-theme contrast) in the same pass rather than just filed for later.

### 2026-08-04 — Scaling to 200 questions in two rounds (DN-5/6, DN-7/8)
- Worked: generating new content in parallel independent-agent batches (2 agents x 50, then another 2 x 50) with explicit quality bars written into the prompt up front (plausible distractors, plain language, realistic point-weighting) worked noticeably better than the original pilot batch — each round's Student Review found fewer and progressively narrower issues, and this round's issues (a sign-number contradiction, near-duplicate questions, one calibration gap) were caught and fixed the same day rather than carried forward as backlog debt.
- Didn't: independent parallel batches don't know about each other's content, so duplicate/overlapping facts slipped through twice in the 100-to-200 round (5 near-duplicate pairs, plus a sign-number used for two different real signs) — cross-batch consistency isn't something a single agent's self-check catches when the two agents never see each other's output.
- Change: when generating multiple parallel batches of new content again, either (a) have each agent read the others' output before finalizing, or (b) always run one merge-time consistency pass (a review agent reading the *combined* new content, not each batch separately) before committing — this round's post-hoc Student Review over the combined 100 caught what per-batch review would have missed. Also: new topics need their filter-label entries added at the same time as content, not as an afterthought — this bit us in the DN-5/6 round and almost repeated itself here, only caught by keeping the same Playwright filter-count check as a standing pre-commit step.

### 2026-08-04 — 5 new locales in one pass (DN-9)
- Worked: splitting translation work into 10 parallel independent agents (5 languages x 2 content-chunks) with a shared, precise prompt (translate from DE canonical, EN as a disambiguation aid only, don't touch non-text fields) got all 200 questions x 5 languages done and schema-validated (zero gaps) in one round, with each agent self-reporting a clean `python3 -m json.tool` pass and exact id-set match before merge.
- Didn't: adding a 3rd/4th/5th/6th/7th language is exactly the kind of change that breaks an implementation quietly written for exactly two — the DE/EN button-pair toggle, and (more seriously) the standalone-preview build script's asset-inlining, which does an exact string match against a specific line of app.js and had gone stale after an unrelated refactor (adding the `pickAlt()` alt-text fallback function) changed that line's exact text. The build silently produced a preview with broken images instead of erroring - only caught because the verification pass happened to include a diagram-bearing question and the image obviously didn't render.
- Change: any code that does exact-string-match patching of another file (like the preview build script patching app.js) needs an assertion that the match actually happened, not a silent no-op fallback - added `assert old_string in js_patched` before each patch in build_standalone_preview.py so future app.js refactors fail loud instead of shipping a broken preview. Also: alt text for images (SIGN_ALT/DIAGRAM_ALT) doesn't automatically grow with new UI languages - it's tracked separately now (DN-28) with an explicit fallback chain so missing translations degrade gracefully instead of breaking.

### 2026-08-04 — User-caught sign bug + UX review of the language picker
- Worked: a real end user (not a persona) caught something both the Developer and every prior review missed - Zeichen 306/307 rendered as a square instead of a diamond, with a border scheme the real sign doesn't have. Auditing all 34 signs on the back of that one report (rather than just patching the one sign) found two more real category mismatches (267, 283/286) that had shipped undetected since DN-2. A fresh independent UX review of the just-shipped 7-language `<select>` (prompted by the PO asking for icons) caught a second real problem before it was implemented: 2-letter codes are unreadable to exactly the low-Latin-literacy audience the new languages were added for.
- Didn't: the original 34-sign visual verification (DN-2's retro log) was a full-grid screenshot review and still missed 3 category errors - a screenshot check catches "is this broken/ugly" reliably but doesn't catch "is this the *legally correct* sign for this number" unless the reviewer (human or agent) is specifically checking each shape against a real reference, not just eyeballing "does this look like a plausible traffic sign." Visual review and factual-accuracy review are different checks and both are needed.
- Change: when the PO's own instinct (icons/flags for the language picker) conflicts with a UX review's finding (flags misrepresent languages), surfaced the tradeoff explicitly rather than either silently overriding the PO's idea or building it uncritically - implemented a middle path (endonym text + a generic non-language-specific icon) and explained why. Also: DN-29 (trial exam) is filed as a scope-change request needing explicit PO sign-off, not built - it reverses DN-13's original non-negotiable "no exam mode" boundary, and per docs/PERSONAS.md only the PO gets to make that call, not an inferred "would even go for" aside.

### 2026-08-04 — 500 questions, 12 locales, exam mode activated (DN-34/DN-35/DN-29)
- Worked: the 9-parallel-agent content round (287→500 questions, 3 brand-new topics) got a genuine cross-batch consistency pass this time before Done, not just an id-collision check like DN-30's batch did — it found and fixed a real sign-name bug (Zeichen 208 mislabeled with 308's name, same bug class as the 306/307 and 133/136 incidents), 3 real cross-batch near-duplicate questions, and several plain-language/tell-distractor issues, all fixed in the same round instead of filed as debt. Locale expansion (7→12 languages, 4000 translations via 25 parallel agents) merged cleanly with zero schema errors on the first pass, because the chunk-file-then-merge pattern from DN-9 scaled without change.
- Didn't: TOPIC_LABELS for the 3 new topics (ladung/erstehilfe/fahrtuechtigkeit) would have shipped completely unlabeled in the filter UI if I hadn't caught it while adding the 5 new locale columns — the 9 content-generation agents had no reason to know a UI-facing labels dict even existed. Also hit a real CSS bug building exam mode: `[hidden]` and a class selector have equal specificity, so `.exam-modal { display: flex }` silently overrode the hidden attribute and the picker modal was stuck visible-but-unclickable-behind-itself — the exact same bug class already documented for `.image-note` earlier in this project, just not generalized into a habit yet.
- Change: any time a new topic/locale is added, grep for every hardcoded per-topic or per-locale dict in app.js up front (TOPIC_LABELS, UI_STRINGS, LANG_PICKER_LABEL, SIGN_ALT) rather than discovering gaps one at a time. Also: any new full-screen modal/overlay div needs an explicit `.foo[hidden] { display: none }` rule from the start, not just class-based show/hide — write it into the CSS the same commit the element is added, since this specificity trap has now bitten the project twice.

### 2026-08-04 — Comprehensive sign catalog (DN-30): 35 -> 122 signs
- Worked: splitting the sign catalog into 4 parallel independent agents by StVO Anlage (Gefahr/Vorschrift/Richt/Zusatz), each REQUIRED to WebSearch-verify any sign it wasn't fully confident about (explicitly citing the 306/307 diamond-vs-square bug as the reason for that requirement), caught a real error before it shipped this time instead of after: Zeichen 410 (Europastrasse) is green, not blue, which needed a whole new shape template. That verification discipline, applied by one of the agents to the general catalog while researching, also surfaced a second real bug in content that had ALREADY shipped since DN-2 (Zeichen 133/136 confused) - proof that "verify before drawing" as a standing instruction pays off beyond just the immediate task.
- Didn't: merging 4 independently-generated Python fragments into one file by hand hit a real self-inflicted problem - an accidental `git checkout` (meant to inspect diff state) silently reverted uncommitted work from earlier in the same session (new shape templates, the 133/136 fix) because they hadn't been committed yet. Caught immediately by re-running validation, but cost a redo. Also: 4 parallel batches picking icon-helper names independently produced one real function-name collision (`symB_bicycle_black` vs `symD_bicycle_black`, both valid but different implementations) - harmless here since both were equivalent, but not guaranteed next time.
- Change: commit checkpoints more aggressively during a long single-session multi-step build (don't let more than one "unit" of work sit uncommitted at once) so an accidental destructive git command has a small blast radius, not a whole afternoon's work. Also: this round's 87 new sign questions were merged by id-collision check ONLY (no cross-batch Student Review), unlike the DN-7/DN-8 content round which caught 5 near-duplicates via exactly that missing step - filed as DN-32 rather than silently skipped, since the lesson from that earlier round clearly still applies here and almost got skipped under time pressure.

### 2026-08-04 — Module/exam-type architecture (DN-39, folds in DN-36)
- Worked: treating the locale-split (DN-36) and the module-split (new "which exam are you studying for" request) as one restructuring rather than two paid off exactly as predicted — both touch the same data-loading path, so building `data/build_modules.py` once to derive `app/data/<exam_type>/{core.json,locales/*.json}` from flat master files solved the payload problem (~5MB monolith → ~250-400KB per visitor) and the module problem (a Klasse-B user never downloads Angelschein content) in the same pass. Naming the scope field generically (`class_scope` for Fuehrerschein, `region_scope` for Angelschein, resolved per-module via `scopeFieldFor()`) meant the two-step picker UI needed zero module-specific branching — it already collapses to one step today (Fuehrerschein has only one class option) and will just work when a real second class or Angelschein region set is added.
- Didn't: building the Angelschein seed content surfaced a real, already-shipped bug rather than a new one — all 12 locales' `UI_STRINGS[*].subtitle` strings had "Klasse B"/"Class B" hardcoded from when the app only had one module, so the first live Playwright run showed "5 Fragen · Klasse B · ..." under an Angelschein selection. Caught by actually clicking through the new picker in a real browser (same discipline as DN-13's lesson), not by reading the diff. Also had to rewrite `build_standalone_preview.py`'s data-inlining from scratch — its old exact-string-fetch-patch approach (already flagged as fragile in DN-9's retro) broke the instant `app/data.json` was deleted, exactly the failure mode that retro warned about.
- Change: any UI string that names a specific class/module inline (not through a data-driven label) is a latent bug once a second module/class exists — grep for hardcoded exam/class names in UI_STRINGS-style dicts before considering a multi-module feature done, the same way DN-34/35's retro already flagged doing this for TOPIC_LABELS/locale dicts. Also: confirmed the DN-9 lesson generalizes — any script that patches another file by exact string match (not just app.js patches) needs a structural approach (map-driven fetch monkeypatch, or an assert-on-match) instead, since "worked once" doesn't mean "survives the next refactor."

### 2026-08-05 — GitHub/Netlify go-live, Motorrad/LKW launch (DN-40), sign QA (DN-41), first real Angelschein batch (DN-11)
- Worked: the DN-39 module architecture paid off exactly as designed the first time it was actually exercised for a genuinely new module — adding Motorrad and LKW needed only two new manifest entries and two `split_module()` calls, zero app.js changes, because `EXAM_TOPIC_DRAW`'s per-exam_type namespacing already had a graceful uniform-fallback built in. Six parallel content agents each writing to an explicit, distinct output path (a hard lesson from an earlier file-collision incident this same round) produced 180 schema-clean questions (Motorrad+LKW) with zero merge problems, and the same pattern repeated cleanly for Angelschein's 90-question DN-11 batch across 6 topic agents.
- Didn't: the project's own tracking docs (BACKLOG.md, the two Claude Project docs) had drifted out of sync with reality — DN-31 was listed as open backlog ("87 sign questions still need uk/pl/ar/zh/hi") when it had actually already been completed as a side effect of the DN-34/35 locale-expansion round; nobody had gone back and checked the box. Caught only because the next task ("translate the sign questions") prompted an actual `python3` check of the live data instead of trusting the board's own claim.
- Change: when a board/backlog claims a gap exists, verify against the actual data before starting work to close it — a two-line Python check against the real JSON is cheap insurance against redoing (or worse, appearing to redo) work that's already done. Also: PO scoped DN-28 (alt-text translation) out entirely this round ("signs are static, they're part of the exam, only the learning material needs translation") — a good example of the board carrying a card that looked open but was actually a closed product question; noted explicitly in BACKLOG.md so it doesn't get silently re-opened by a future session that only reads "translate SIGN_ALT" at face value.
